We now set out an architectural approach to building conversational agents, using a chatbot which discusses football data as an example. The aim is to maintain conversational state, while providing LLMs with dynamically relevant information, i.e. context which allows them to answer questions. The approach we adopt builds separate LLM agents, each of which can answer about ten different questions (i.e. has ten functions), and that are coordinated by a receptionist for context switching. We combine this agent architecture with the [wordalisation](/p/e6d046e3786c824bbeb201094e1dcdaf) approach, which turns data into engaging sentences, and text embeddings, which ensures the most relevant context is provided to the agents. 

## Background

The most common way to utilise large language models is through [chat completion](https://huggingface.co/docs/inference-providers/tasks/chat-completion). Suppliers such as OpenAI, Google Gemini and Anthropic Claude provide an API, to which an application sends a conversation history (or its beginning) and receives generated tokens. This conversation history consists of system messages --- which define the LLM's behavior and personality (e.g., "You're a helpful assistant"), then a series of user questions and assistant answers (known as few shot prompts), which reflect the type of questions and answers we might expect from the application and/or previous interactions with the application. Chat completion is the tool we have utilised thus [thus far in the course](38e046e3786c8343b14b0112546ea296.md).

Language model APIs are also capable of** function calling**, where a list of predefined functions is provided along with a chat history with a user, and the [API returns the function](https://developers.openai.com/cookbook/examples/fine_tuning_for_function_calling) that the user most likely wants to activate (see for example [Wang, 2025](https://dl.acm.org/doi/pdf/10.1145/3788284)). Function calling can be accompanied by **parameter extraction**, where the model identifies the required arguments for that function. A further capability of these services is **embedding search**, which involves converting text into high-dimensional vector representations (embeddings) that capture semantic meaning, allowing to identify similarity of sentences or short segments of text (good first reference for this is [Reimers 2019](https://aclanthology.org/D19-1410.pdf)). 

Together, these four LLM services – chat completion, function calling, parameter extraction, and embedding search – can facilitate highly interactive and seemingly intelligent applications. However, an inherent limitation of all of them is their statelessness. Each request to the API is treated as new, with no memory of previous interactions. Enabling coherent conversations involves storing all message—user inputs and LLM responses—associated with a unique user ID and chat ID and resubmitting this to the API each time the user makes a new query. In addition to statelessness, LLMs have a knowledge problem: they operate with a training cut-off date and lack specific, real-time, or proprietary data. The challenge then, in building an application, is to use LLM services in a way that brings new and relevant information into the conversation in a [structured way](https://dl.acm.org/doi/pdf/10.1145/3698590?utm_source=consensus).

Here we are going to focus only on conversations. The challenge is to put together a set of question answer pairs that will allow the chatbot (or analyst as we will call it) to answer the question in the best possible way. We now describe how we do this in Earpiece. In the next section we go into more detail about how embedding, annotation (which underlies parameter extraction) and function calling work in practice.  

## Analysts

If you have used Earpiece Hub you should understand what an analyst is. 

![[Screenshot_2025-07-11_at_16.25.29.png]]

The analyst can summarise players, matches or seasons and answer questions about them using data. 

![[Screenshot_2025-07-11_at_16.28.00.png]]

We can think of an **Analyst** as a combination of a **Context Object**—which tracks the subject of the conversation with uniquely identifiable information like a player ID or match ID—and a **List of Functions** that can be executed based on user queries. Different analysts are specialized for distinct subjects; for example, the Scout Player Analyst manages player-related queries with a context of a season, while the Match Analyst handles match-specific discussions in the context of a single match. One subtlety is that a Twelve Analyst (as experienced by the user) may consist of several sub-analysts in the code, each of which provides specialised skills. For example, when we ask the Scout Player analyst to compare two players, it calls the Compare Player analyst (without telling the user).

To facilitate switches between these specialized analysts, **Redirect Functions** are used to establish the new context and instantiate the appropriate analyst. A central **Receptionist **coordinates these transitions; it is the first analyst a user interacts with and contains redirect functions to all other analysts. If a specialized analyst detects a context switch, it first redirects to the Receptionist, which then directs to the new appropriate analyst. This architecture allows Earpiece to a provide a coherent user experience across different platforms. In the Earpiece hub the experience makes explicit the use of different agents, but this is hidden in the WhatsApp version which only allows scouting.

## The receptionist

The Receptionist of the Hub has the following overall instructions limiting its actions to calling other analysts.

```javascript
  f"You have been called because another analyst in the platform was unable to give the user the information they were looking for."
  f"The analyst provided the following summary of the previous conversation: '{self.context.summary}'.",
  f"The very last thing the user said, which caused the analyst to call you, was: '{self.context.query}'.",
  "Your ONLY valid actions are: (1) call the most appropriate analyst immediately ",
  "OR (2) ask the user a specific clarifying question to determine which analyst is appropriate.",
  "OR (3) explain how the platform works, if the user asks a question about the platform.",
  "You MUST NOT greet the user, chit-chat, or respond in any other way. ",
```

In Earpiece Hub, the remaining instructions ensure that only analysts which the user has access to can be called. When other analysts call the Receptionists it takes the conversation and tries to find the right analyst to answer that question. Code for the analyst is [here](https://github.com/twelvefootball/twelve-chat-api-prototype/blob/dev/api/src/analysts/receptionist/analyst.py). 

![[Screenshot_2025-07-21_at_14.42.56.png]]

A key reason for us having the Receptionist is that there are performance limitations to function calling. Both [scientific research](https://openreview.net/pdf?id=LNxVGPedFW) and [forums](https://community.openai.com/t/how-many-different-function-calls-can-a-model-learn-how-to-do/807943/9) seem to confirm this, although it isn’t entirely sure what the limits are. In any case, the idea of the receptionist and the analysts is to break down the entire functionality of Twelve Earpiece into manageable parts that we know work. One way to think of a chatbot in this way is as an interactive “choose your own adventure”. The receptionist takes you on an adventure with the Match Analyst, when the Match Analyst sends you back to the Receptionist who then finds another analyst who can answer your question.

## Redirect functions

Once the receptionist has worked out which analyst can best help the user, the next challenge is to parameterise the context with the correct information. [OpenAI supports parameterised  function calls](https://platform.openai.com/docs/guides/function-calling?api-mode=responses), but there remain challenges. There are around a hundred thousand players in the databases we use. Just like there are limitations to the number of functions that can be called, there are also limitations to the number of enumerated parameters that can be read into functions. Open AI recommend having less than [20 enumerated parameter values when calling a function](https://platform.openai.com/docs/guides/function-calling?api-mode=responses) and [benchmarks again indicate](https://arxiv.org/pdf/2310.03128) that success falls off rapidly as number of possible values increases. Our solution to this is to create a seperate player and team identification searches. 

![[Screenshot_2025-07-21_at_14.43.32.png]]

We ask GPT4o to return the player name as a string and then we use a separate function to obtain a list of potential player IDs from that string based on fuzzy search. Once we have this list, we again present the possibilities to GPT4o to decide the best option. More details for player name search can be found [here](/192fdb4493c580738b6bea1757f2862c).

There are three types of functions. The first is a summary, which is usually presented whenever the analyst is called: it provides a specific summary wordalisation. The second also provides a standard visualisation and wordalisation of a specific quality, performance on an area of the pitch or a development over time. The third and final type of function gathers together relevant information and answers a question directly.

```python
The match Internazionale 4 - 0 Atalanta, was played on 2024-08-30 20:45:00 (gameweek 3) in the Serie A. \n\n

Compared to their other matches, Internazionale can be satisfied with the outcome of the match. 
Internazionale did not concede any goals. Internazionale scored 3 goals: at 56 minutes, 47 minutes and 10 minutes.

Internazionale completely dominated during the opening 15 minutes of the second half. 
Atalanta dominated during the middle of the second half. 
Internazionale dominated during the last part of the second half. 

```

The approach here is to create a long document describing all of the relevant information for answering the question. The challenge is to get the relevant information both from the data and from the text we have written about matches and players. Here we use embeddings.
